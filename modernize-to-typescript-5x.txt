Modernizing janux-people.js Build Process
Date: 2026-03-19
Updated: 2026-03-31

Overview
--------
Replace the Node 12 + Gulp 4 build pipeline with a modern Node 20 + npm scripts
setup using the TypeScript compiler directly. The goal is to eliminate unnecessary
build tool abstraction for a library that only needs to transpile TypeScript to
CommonJS with declaration files.

Current Stack
-------------
- Node 12
- TypeScript 3.1.8
- Gulp 4 (orchestration)
- gulp-typescript (TS compilation)
- gulp-tslint + TSLint (linting) [NOTE: TSLint is abandoned]
- del (directory cleaning)
- gulp-mocha + Mocha 2.x (testing)
- gulp-typedoc + TypeDoc 0.8.0 (documentation)

Target Stack
------------
- Node 20 (runtime is Node 22; engines field set to >=20)
- TypeScript 5.x
- npm scripts (orchestration)       — replaces Gulp entirely
- tsc directly (compilation)        — replaces gulp-typescript
- ESLint + @typescript-eslint (linting) — replaces abandoned TSLint
- rimraf (directory cleaning)       — replaces del/clean tasks
- Vitest + Chai (testing)           — replaces gulp-mocha + Mocha 2.x
- TypeDoc (documentation)           — replaces gulp-typedoc

Why Drop Gulp?
--------------
The current Gulp tasks are minimal: clean, lint, compile, test, watch, and docs.
None of these require a streaming build system. The TypeScript compiler handles
compilation and watch mode natively, and npm scripts can orchestrate the remaining
steps. Removing Gulp eliminates a layer of abstraction and several dependencies
(gulp, gulp-load-plugins, gulp-load-subtasks, gulp-typescript, gulp-tslint,
gulp-sourcemaps, gulp-concat, gulp-mocha, gulp-typedoc).

Why Not tsup / esbuild / Rollup / Vite?
----------------------------------------
Those tools are valuable for bundling (tree-shaking, ESM/CJS dual output, asset
handling). This project only transpiles TypeScript to CommonJS with declaration
files — tsc does this natively with zero overhead or configuration complexity.

Why Vitest Instead of Mocha + ts-node?
---------------------------------------
Node 22 ships with built-in TypeScript type-stripping. When Mocha loads a .ts
test file via import(), Node 22 intercepts the call, strips the types, and treats
the file as an ES module — bypassing ts-node and tsx entirely. Any test file that
contains a require() call then fails at runtime because require is not defined in
ES module scope. This is a fundamental incompatibility between Mocha's module-
loading strategy and Node 22's native TypeScript support.

Vitest avoids this entirely. It has native TypeScript support via its own transform
pipeline and does not depend on ts-node, tsx, or Node's module hook chain. Test
files are transformed transparently before execution, with no ESM/CJS conflicts.

Vitest is also Jest API-compatible, so test files require only minimal changes:
swap require() for import, update import paths, and add three vitest imports
(describe, it, beforeEach). All Chai assertion chains (expect(x).to.equal(y)
etc.) remain unchanged because Chai is retained as the assertion library.

Why Keep Chai?
--------------
The existing test assertions are written in Chai's BDD style (.to.equal, .to.be
.instanceof, etc.). Rewriting them to Vitest's native expect (toBe, toEqual, etc.)
would be mechanical churn with no benefit. Chai works fine alongside Vitest:
Vitest provides the test lifecycle; Chai provides the assertions.

Summary of Key Decisions
-------------------------
- lodash moved to dependencies (used in src/); follow-up: evaluate eliminating it
- generator/ excluded from published package; kept in repo for future publication
  as a separate utility package (e.g. janux-people-testdata)
- generator/ and its test files are OUT OF SCOPE for this migration; see the
  FOLLOW-UP section below
- strict: true in tsconfig.json; enabled incrementally flag-by-flag in Phase 8
- Removed obsolete deps: browserify, vinyl-source-stream, express, amdefine
- q and bluebird removed; generator/ refactoring deferred to a future project
- src/index.ts replaces hand-maintained root index.js and index.d.ts
- src/collections.ts (vendored basarat/typescript-collections) removed; see Phase 3

Phase 3 — Remove basarat/collections
------------------------------------------------------------------------------
Goal: eliminate src/collections.ts (a vendored copy of basarat/typescript-
collections) and all references to it across src/. No public API changes.

Background:
  src/collections.ts is a 2700-line vendored copy of the basarat/typescript-
  collections library included directly in the repo rather than as an npm
  package. It is used in two ways across src/impl/:
    1. collections.makeString(this) — called in toString() on every impl class;
       produces a "{prop:val,...}" string from own properties.
    2. Dictionary<string, ContactMethod> — used as the return type and internal
       implementation of the protected createContactMethodDictionary() method
       in PartyAbstract. The public methods that call it (postalAddresses(),
       phoneNumbers(), emailAddresses()) already return `any`.
  The api/ interfaces do not expose either type; the changes are entirely
  internal to impl/.

Files to update:
  src/api/Party.ts
    - Remove the three dead import lines:
        /// <reference path="../collections.ts" />
        import basarat = require('../collections');
        import collections = basarat.collections;
      (None of the types from collections are used in this file.)

  src/impl/Party.ts
    - Remove:
        /// <reference path="../collections.ts" />
        import basarat = require('../collections');
        import collections = basarat.collections;
        import Dictionary = collections.Dictionary;
    - In createContactMethodDictionary():
        Change return type:  Dictionary<string, ContactMethod>
                         →   Record<string, ContactMethod>
        Change constructor:  new Dictionary<string, ContactMethod>()
                         →   {} as Record<string, ContactMethod>
        Change setter:       contacts.setValue(contact.type, contact)
                         →   contacts[contact.type] = contact
    - In toString():
        Change: return collections.makeString(this);
             →  return JSON.stringify(this);

  src/impl/PhoneNumber.ts
  src/impl/PartyName.ts
  src/impl/StateProvince.ts
  src/impl/PostalAddress.ts
  src/impl/Country.ts
  src/impl/PersonName.ts
  src/impl/City.ts
    For each of the above:
    - Remove:
        /// <reference path="../collections.ts" />
        import basarat = require('../collections');
        import collections = basarat.collections;
    - In toString():
        Change: return collections.makeString(this);
             →  return JSON.stringify(this);

Files to delete:
  src/collections.ts

Files to update:
  test/Person.spec.ts

Phase 6 — Eliminate lodash dependency
------------------------------------------------------------------------------
Goal: remove lodash from dependencies (and devDependencies) entirely.

Background:
  lodash is currently declared as a runtime dependency in package.json, which
  means it is shipped to every consumer of this library. However, a search of
  the entire src/ tree reveals zero lodash calls — it is not imported anywhere
  in the library source. The only usages in this repo are:

    test/Person.spec.ts         _.isObject(person)         — one call
    test/Organization.spec.ts   _.isObject(org)            — one call
    test/UserService.spec.js    require('lodash')          — imported, never called
    generator/user-dao.js       _.cloneDeep(userObj)       — one call
    generator/user-service.js   _.isObject(instance)       — one call

  The test/ usages are trivially replaced with native equivalents.
  The generator/ usages are deferred to the Generator Refactoring project
  (see FOLLOW-UP section), but because generator/ is excluded from the
  published package they do not block removal of lodash from dependencies.

Files to update:
  test/Person.spec.ts
    - Remove: import _ from 'lodash';
    - Change: expect(_.isObject(person)).to.equal(true)
           →  expect(person instanceof Object).to.equal(true)

  test/Organization.spec.ts
    - Remove: import _ from 'lodash';
    - Change: expect(_.isObject(org)).to.equal(true)
           →  expect(org instanceof Object).to.equal(true)

  package.json
    - Remove from dependencies:    "lodash": "^4.17.21"
    - Remove from devDependencies: "@types/lodash": "^4.17.0"

Note on test/UserService.spec.js:
  This file requires lodash but never calls any lodash method. The dead
  require() line will be removed as part of the Generator Refactoring project

Phase 7 — Remove ESLint Disable Statements
------------------------------------------------------------------------------
Goal: remove all eslint-disable comments in src/ file by file, fixing the
underlying issues so the code complies cleanly with ESLint. This phase
prepares src/ for incremental TypeScript strict mode enablement (Phase 8).

Background:
  Phase 4 introduced ESLint with @typescript-eslint rules. The initial
  linting pass revealed issues that were suppressed with eslint-disable
  comments rather than fixed. Removing these comments forces us to address
  the underlying code issues, resulting in cleaner, more maintainable code
  and catching potential bugs early.

Audit results (grep -r "eslint-disable" src/):
  src/impl/PartyAbstract.ts       /* eslint-disable @typescript-eslint/no-explicit-any */
  src/impl/PersonName.ts          /* eslint-disable @typescript-eslint/no-explicit-any */
  src/impl/Organization.ts        /* eslint-disable @typescript-eslint/no-explicit-any */
  src/impl/Person.ts              /* eslint-disable @typescript-eslint/no-explicit-any */
  src/api/PersonName.ts           // eslint-disable-next-line @typescript-eslint/no-explicit-any

  Total files: 5 (4 impl/, 1 api/)
  Suppressed rule: @typescript-eslint/no-explicit-any
  Comment style: block-level (/* */) in impl/, line-level (//) in api/

Process (file by file):
  1. Start with the file that has the fewest suppressions.
  2. For each suppression:
     a. Understand why the linter flagged the code (e.g., no-explicit-any,
        unused-vars, etc.)
     b. Fix the code to comply with the rule (e.g., add explicit type
        annotations, remove unused imports)
     c. Verify that npm run lint no longer complains about that line
     d. Remove the eslint-disable comment
  3. After all suppressions are removed from the file:
     a. Run npm run lint to confirm the file is clean
     b. Run npm run build to ensure compilation still works
     c. Run npm test to ensure tests still pass
     d. STOP and request review of your changes before committing
  4. Once changes are reviewed and committed, move to the next file.

Expected outcomes per file:
  - All eslint-disable / @ts-expect-error / @ts-ignore comments removed
  - Code is more explicit (types added, unused code removed)
  - npm run lint, npm run build, and npm test all pass

Verification (after all files are clean):
  npm run lint     — no warnings or errors; no suppression comments remain
  npm run build    — compiles cleanly
  npm test         — all tests pass

  .eslintrc.json update (final step):
    Promote "@typescript-eslint/no-explicit-any" from "warn" to "error"
    to lock in the improvement and prevent future regressions.
    Confirm npm run lint still passes after the rule change.

Phase 8 — Enable TypeScript Strict Flags
------------------------------------------------------------------------------
Goal: incrementally enable TypeScript's strict mode flags in tsconfig.json,
fixing all errors at each step, until "strict": true can be set cleanly.
This is the capstone of the modernization effort.

Background:
  Phase 1 set "strict": false deliberately to unblock compilation. Phase 7
  cleaned up all no-explicit-any suppressions. With those out of the way,
  the codebase is ready for strict mode to be layered in one flag at a time.

  TypeScript's "strict": true is shorthand for enabling all of the following
  individual flags simultaneously. Enabling them one at a time keeps each
  batch of errors small and reviewable:

    noImplicitAny              — ban implicit any; require explicit types
    strictNullChecks           — null and undefined are not assignable to
                                 other types unless explicitly declared
    strictFunctionTypes        — stricter checking of function parameter types
    strictBindCallApply        — type-safe .bind(), .call(), and .apply()
    strictPropertyInitialization — class properties must be initialised in
                                 the constructor (requires strictNullChecks)
    noImplicitThis             — error on 'this' with an implicit 'any' type
    alwaysStrict               — emit 'use strict' in output files

Process (flag by flag):
  For each flag in the order listed above:
  1. Add the flag (set to true) in tsconfig.json compilerOptions.
  2. Run npm run build.
  3. Fix all TypeScript errors introduced by the flag.
  4. Run npm test to confirm no regressions.
  5. STOP and request review of your changes before committing.
  6. Once changes are reviewed and committed, move to the next flag.

  Final step:
    Replace all individual strict flags in tsconfig.json with the single
    "strict": true setting, confirm npm run build and npm test still pass,
    and update the Summary of Key Decisions to reflect that strict mode
    is now fully enabled.

Verification (after each flag):
  npm run build    — no TypeScript errors
  npm test         — all tests pass

Verification (final):
  tsconfig.json contains "strict": true and no individual strict flags
  npm run build    — compiles cleanly
  npm run lint     — no warnings or errors
  npm test         — all tests pass
